# EXECUTION PROTOCOL — پروتکل اجرا، توسعه و تحویل

**نسخه:** 1.1.0  
**وضعیت:** بازسازی‌شده بر اساس تصمیمات تأییدشده مالک پروژه

## 1. هدف
برای توسعه، کدنویسی، بازطراحی، تست، رفع خطا، تغییر مستندات، Git و آماده‌سازی استقرار. عامل مستقل عمل می‌کند، اما مخزن اصلی، داده‌ها، سرمایه و محیط عملیاتی را در برابر تغییر غیرمجاز محافظت می‌کند.

## 2. مأموریت و معیار پذیرش
پیش از تغییر، هدف، محدوده، خروجی و معیار پذیرش، رفتار فعلی، محدودیت‌های صریح، موارد خارج از محدوده، وابستگی‌ها، ریسک‌ها و تأییدهای لازم را مشخص کن.
اگر درخواست صرفاً ماژولارکردن یا بازآرایی است، رفتار موجود را بدون مجوز تغییر نده؛ از جمله ترتیب عملیات، اعداد، آدرس‌ها، پارامترها، retryها، حجم‌ها، زمان‌بندی و منطق تراکنش.

## 3. بررسی اولیه مخزن
پیش از ویرایش:
- مخزن، شاخه پیش‌فرض، آخرین commit و working tree را شناسایی کن؛
- ساختار، زبان‌ها، معماری، وابستگی‌ها، نقاط ورود و پیکربندی را بخوان؛
- تست‌ها، CI، اسکریپت‌ها و مستندات را بررسی کن؛
- PRها، Issues و کارهای موازی مرتبط را بررسی کن؛
- قابلیت‌های واقعی را از ادعاهای مستندات تفکیک کن.
مستندات قدیمی را بدون تطبیق با کد و وضعیت زنده مبنا قرار نده.

## 4. نسخه کاری مستقل و حفاظت از main
تمام تغییرات و آزمایش‌ها باید در نسخه کاری مستقل انجام شوند. بر اساس شرایط از clone، branch، worktree، fork یا کپی کنترل‌شده استفاده کن.
برای این مخزن:
- شاخه اختصاصی از آخرین main بساز؛
- مستقیماً روی main commit یا push نکن؛
- تغییرات در حال انجام دیگران را بازنویسی نکن؛
- تغییرات را محدود و قابل بازبینی نگه دار؛
- برای تغییرات PR بساز؛
- Merge، انتشار، تغییر محیط عملیاتی یا حذف مخزن بدون تأیید صریح ممنوع است.
دسترسی push مجوز push به شاخه اصلی نیست.

## 5. طراحی و پیاده‌سازی
معماری و قراردادهای موجود را بررسی کن؛ ساده‌ترین راهکار سازگار را انتخاب کن؛ framework، سرویس یا وابستگی غیرضروری اضافه نکن؛ مسئولیت‌ها و تست‌پذیری را رعایت کن؛ تغییر ناسازگار را شناسایی کن؛ تصمیم معماری بین‌ماژولی را ثبت کن؛ از scope creep پرهیز کن؛ کد، تست و مستندات را هماهنگ به‌روز کن.

## 6. تست و اعتبارسنجی
متناسب با مأموریت از unit، integration، functional/acceptance، API/RPC، static analysis، lint، type checking، regression، migration/data integrity، security/dependency، performance و environment/deployment tests استفاده کن.
برای هر تست، فرمان/روش، محیط و نسخه ابزار، نتیجه واقعی، تعداد موفق/ناموفق/ردشده، خطاها و محدودیت اجرا را ثبت کن.
تست محلی را با CI یا تست عملیاتی یکی ندان. تست اجرا نشده باید NOT RUN یا NOT VERIFIED گزارش شود.

## 7. شدت خطا
- CRITICAL: خطر جدی برای امنیت، دارایی، داده یا پایداری؛
- HIGH: نقص مهم یا مانع اصلی؛
- MEDIUM: نقص قابل توجه با راهکار جایگزین؛
- LOW: اثر محدود یا غیرمسدودکننده؛
- INFORMATIONAL: هشدار یا نکته بدون نقص عملیاتی مشخص.

خطای کم‌اهمیت نباید بی‌دلیل کل مأموریت را متوقف کند. خطر جدی موجب توقف اقدام پرخطر و ارزیابی مجدد است.

## 8. تلاش برای رفع خطا
برای هر راهکار مشخص، پیش‌فرض حداکثر سه تلاش معنادار است. تکرار بدون تغییر شرایط تلاش جدید نیست. پس از شکست، راهکار جایگزین منطقی را بررسی کن. تلاش بی‌پایان ممنوع است. اگر رفع خطا خارج از محدوده یا نیازمند مجوز است، متوقف و گزارش کن.
برای هر خطای مهم شرح و اثر، علت احتمالی، راهکارهای امتحان‌شده، تعداد تلاش، نتیجه، علت شکست، راهکار باقی‌مانده و وضعیت نهایی را ثبت کن.

## 9. امنیت و عملیات واقعی
به‌صورت پیش‌فرض از کلید خصوصی، seed phrase، رمز عبور یا token واقعی در کد، log، fixture و مستندات استفاده نکن؛ اطلاعات محرمانه را commit نکن؛ API/RPC را فقط در محدوده read-only مجاز به کار ببر؛ از mock، sandbox، testnet و paper trading استفاده کن؛ قابلیت live را غیرفعال نگه دار.
بدون تأیید صریح و مشخص مالک، ارسال سفارش واقعی، انتقال دارایی، تراکنش واقعی، امضای کیف پول، استفاده از سرمایه واقعی، اجرای production، تغییر سرور عملیاتی یا فعال‌سازی live trading ممنوع است. برای اثبات عملکرد با دارایی واقعی آزمایش نکن.

## 10. Git و Pull Request
شاخه اختصاصی از آخرین main بساز؛ diff را بازبینی کن؛ پیام commit روشن بنویس؛ تغییرات را در commitهای معنادار دسته‌بندی کن؛ PR به main بساز و هدف، محدوده، تصمیمات، تست‌ها، ریسک‌ها و محدودیت‌ها را توضیح بده؛ شواهد CI را درج کن. بدون تأیید صریح مالک PR را Merge نکن. بازبین مستقل را جایگزین خودت نکن.

## 11. مستندات پایدار
مستندات موجود را توسعه بده و نسخه موازی متناقض نساز. بر اساس ساختار پروژه، فایل‌های MASTER.md، CURRENT_STATE.md، DECISIONS.md، CHANGELOG.md، TODO.md، TEST_REPORT.md، ERROR_LOG.md و HANDOFF.md یا معادل‌های موجود را نگهداری کن.
در این مخزن از PROGRESS.md و docs/agents/IMPLEMENTATION_STATE.md استفاده کن؛ آن‌ها را بدون دلیل جایگزین نکن. مستندات را پس از هر مرحله منطقی و مهم به‌روز کن، نه فقط در پایان.

## 12. گزارش انتقال (HANDOFF)
حداقل شامل نام مخزن و مأموریت، هدف و محدوده، شاخه اصلی و کاری، آخرین commit و PR، آخرین مرحله تأییدشده، اقدامات انجام‌شده، فایل‌های تغییرکرده، تست‌ها و نتایج، خطاها و تلاش‌ها، تصمیمات و فرضیات، محدودیت‌ها و موارد تأییدنشده، اقدامات باقی‌مانده، گام بعدی دقیق، فرمان‌های ادامه و تأییدهای لازم باشد.
عامل بعدی باید HANDOFF را با وضعیت واقعی GitHub تطبیق دهد؛ HANDOFF به‌تنهایی جایگزین بررسی مخزن نیست.

## 13. معیار پایان
درخواست و معیارهای پذیرش پوشش داده شده، تغییرات در محدوده، تست‌های ضروری اجرا و گزارش شده، خطاهای مهم تعیین تکلیف، مستندات به‌روز، مخزن اصلی و production محفوظ، وضعیت PR شفاف و محدودیت‌ها/ریسک‌ها/موارد تأییدنشده اعلام شده باشند.
اگر بخشی به علت دسترسی یا مجوز انجام نشده، وضعیت COMPLETED - NOT VERIFIED یا BLOCKED باشد، نه VERIFIED.
