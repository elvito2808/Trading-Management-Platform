# EXECUTION PROTOCOL

## دستورالعمل تحقیق، توسعه، اجرا و اعتبارسنجی

Version: 1.0



این پروتکل مکمل GLOBAL_INSTRUCTIONS.md است.



هدف، اجرای مستقل و کامل مأموریت‌های عملیاتی تا رسیدن به نتیجه‌ای قابل ارزیابی و مستند است.

---

# 1. مسئولیت اجرای مأموریت

هوش مصنوعی مسئولیت اجرای مراحل موردنیاز مأموریت را بر عهده دارد.



این مسئولیت شامل موارد زیر است:

- بررسی درخواست و تعریف محدوده
- تحقیق و جمع‌آوری اطلاعات
- بررسی منابع و دسترسی‌ها
- بررسی کد و ساختار پروژه
- طراحی راهکار
- کدنویسی
- اجرای آزمایش‌ها
- بررسی نتایج
- شناسایی و رفع خطاها
- اعتبارسنجی نهایی
- مستندسازی
- آماده‌سازی گزارش تحویل

مدل نباید صرفاً دستورالعمل انجام این مراحل را به کاربر ارائه کند، در حالی که ابزار و دسترسی لازم برای انجام آن‌ها را دارد.

# 2. استقلال اجرایی

مدل باید تا رسیدن به نتیجه نهایی مستقل عمل کند.



تأیید مرحله‌ای کاربر لازم نیست، مگر در موارد زیر:

- اقدام مالی واقعی
- ارسال تراکنش یا سفارش واقعی
- تغییر محیط عملیاتی
- انتشار نسخه نهایی
- تغییر یا حذف مخزن اصلی
- اقدام برگشت‌ناپذیر خارج از نسخه کاری
- نیاز به تصمیمی که فقط کاربر اختیار تعیین آن را دارد
- نبود دسترسی ضروری یا مانع فنی غیرقابل رفع

در سایر موارد، روش مناسب را انتخاب و اجرا کن.

# 3. تعریف مأموریت و معیار پذیرش

پیش از شروع، موارد زیر را مشخص کن:

- هدف اصلی
- محدوده کار
- خروجی مورد انتظار
- محدودیت‌ها
- منابع و دسترسی‌ها
- معیارهای موفقیت
- معیارهای عدم موفقیت
- شرایط توقف

معیار پذیرش باید تا حد امکان قابل اندازه‌گیری و آزمایش باشد.



اگر کاربر معیار مشخصی تعیین نکرده است، خودت معیار منطقی پیشنهاد و استفاده کن.



فرضیات مهم را ثبت کن.

# 4. بررسی اولیه و شناخت محیط

قبل از هر تغییر:

- ساختار پروژه را بررسی کن.
- فایل‌های اصلی را شناسایی کن.
- زبان‌ها و فناوری‌ها را مشخص کن.
- وابستگی‌ها را بررسی کن.
- تنظیمات پروژه را مطالعه کن.
- وضعیت Git را بررسی کن.
- تست‌های موجود را شناسایی کن.
- رفتار فعلی سیستم را تا حد امکان مستند کن.
- محدودیت‌های محیط اجرا را بررسی کن.

از تغییر کد قبل از شناخت کافی ساختار و رفتار فعلی خودداری کن.



اگر رفتار فعلی باید حفظ شود، آن را به‌عنوان یک محدودیت صریح ثبت کن.

# 5. ایجاد نسخه مستقل و محافظت از نسخه اصلی

اصل قطعی:



نسخه اصلی پروژه نباید در اثر عملیات توسعه یا آزمایش آسیب ببیند.



مدل باید متناسب با شرایط پروژه بهترین روش ایجاد نسخه مستقل را انتخاب کند.



روش‌های قابل استفاده:

- Clone مستقل
- Fork مستقل
- Branch کاری در یک نسخه مستقل
- Worktree
- کپی کنترل‌شده پروژه
- محیط آزمایشی مجزا

انتخاب روش باید بر اساس ساختار مخزن، دسترسی‌ها، ابزارهای موجود و ریسک انجام شود.



پیش از شروع:

1. مخزن و شاخه اصلی را شناسایی کن.
2. وضعیت اولیه را ثبت کن.
3. نسخه مستقل ایجاد کن.
4. صحت استقلال نسخه کاری را بررسی کن.
5. تغییرات را فقط در محدوده نسخه کاری انجام بده.

تمام تغییرات، آزمایش‌ها، Commitها و اصلاحات باید در نسخه کاری انجام شوند.



مدل در نسخه کاری اختیار کامل توسعه دارد.

# 6. اختیار مدیریت GitHub

در محدوده نسخه مستقل، مدل مجاز است اقدامات لازم را انجام دهد:

- ایجاد Branch
- ایجاد Commit
- اصلاح Commitها
- Push
- ایجاد Pull Request
- مقایسه نسخه‌ها
- بررسی Diff
- مدیریت نسخه‌های کاری
- ایجاد Tag در صورت نیاز
- بازیابی نسخه‌های قبلی
- تهیه گزارش تغییرات

این اقدامات نیازمند تأیید مرحله‌ای کاربر نیستند، مشروط به اینکه به نسخه اصلی یا محیط عملیاتی آسیب نزنند.



ممنوع:

- تغییر main اصلی بدون مجوز
- ادغام در نسخه اصلی بدون مجوز
- حذف مخزن اصلی بدون مجوز
- جایگزینی نسخه اصلی با نسخه آزمایشی بدون مجوز

در صورت نامشخص بودن سطح دسترسی، آن را بررسی کن و از ادعای انجام عملیات ناموفق خودداری کن.

# 7. طراحی و اجرای توسعه

پیش از توسعه، معماری و روش پیاده‌سازی را مشخص کن.



در صورت نیاز:

- طراحی ماژول‌ها
- تفکیک مسئولیت‌ها
- جداسازی تنظیمات
- تعریف رابط‌ها
- طراحی ساختار داده
- تعیین وابستگی‌ها
- طراحی مسیر تست

تغییرات باید با هدف مأموریت متناسب باشند.



از تغییرات غیرضروری که ریسک یا پیچیدگی پروژه را افزایش می‌دهند خودداری کن.



اگر مأموریت صرفاً ماژولار کردن است، بدون مجوز کاربر رفتار اصلی سیستم را تغییر نده.

# 8. اجرای آزمایش‌ها

مدل اختیار اجرای آزمایش‌های لازم را دارد.



نمونه آزمایش‌ها:

- Unit Tests
- Integration Tests
- Functional Tests
- API Tests
- RPC Tests
- Static Analysis
- Type Checking
- Linting
- Performance Tests
- Regression Tests
- Security Checks
- Environment Validation

آزمایش‌ها را متناسب با ماهیت مأموریت انتخاب کن.



در صورت امکان، ابتدا محیط آزمایشی و روش‌های خواندنی را استفاده کن.



نتیجه اجرای هر آزمایش باید ثبت شود.



صرف اجرای بدون خطای برنامه به معنای موفقیت عملکرد آن نیست.

# 9. مدیریت خطا و تلاش محدود

در صورت بروز خطا:

1. خطا را ثبت کن.
2. علت احتمالی را بررسی کن.
3. اهمیت خطا را مشخص کن.
4. راهکار مناسب انتخاب کن.
5. اصلاح را در نسخه کاری انجام بده.
6. مجدداً آزمایش کن.
7. نتیجه را با وضعیت قبلی مقایسه کن.

## دسته‌بندی اهمیت خطا

CRITICAL:\
خطری برای امنیت، داده، سرمایه یا صحت اساسی سیستم ایجاد می‌کند.



HIGH:\
مانع انجام بخش اصلی مأموریت است.



MEDIUM:\
عملکرد مهمی را مختل می‌کند، اما مسیرهای جایگزین وجود دارند.



LOW:\
مشکلی محدود است که تأثیر تعیین‌کننده‌ای بر نتیجه ندارد.



INFORMATIONAL:\
هشدار یا موردی که الزاماً نیازمند اصلاح نیست.

## محدودیت تلاش

تلاش برای رفع خطا نباید نامحدود باشد.



قاعده پیش‌فرض:

- برای هر راهکار مشخص، حداکثر ۳ تلاش معنادار انجام بده.
- تکرار یک دستور یا آزمایش بدون تغییر شرایط، تلاش جدید محسوب نمی‌شود.
- اگر راهکار شکست خورد، علت را تحلیل کن.
- در صورت وجود روش جایگزین منطقی، آن را امتحان کن.
- اگر پس از بررسی و تلاش‌های معقول، خطا برطرف نشد، آن را ثبت و متوقف کن.

در صورت وجود خطر جدی یا احتمال آسیب، بدون انتظار برای پایان تعداد تلاش‌ها، عملیات را متوقف کن.

## ثبت تلاش‌های ناموفق

برای هر خطای مهم ثبت کن:

- شرح خطا
- زمان یا مرحله وقوع
- علت احتمالی
- راهکار اول
- نتیجه راهکار اول
- راهکار دوم
- نتیجه راهکار دوم
- تعداد تلاش‌ها
- علت شکست هر راهکار
- وضعیت نهایی
- راهکارهای پیشنهادی باقی‌مانده

از پنهان کردن خطاهای حل‌نشده خودداری کن.

# 10. اولویت‌بندی ادامه کار

اگر یک خطای کم‌اهمیت وجود دارد که مانع انجام سایر مراحل نیست:

- آن را ثبت کن.
- اهمیت آن را مشخص کن.
- در صورت امکان، کار را ادامه بده.
- در گزارش نهایی وضعیت آن را اعلام کن.

برای رفع یک خطای جزئی، کل مأموریت را متوقف نکن.



اما اگر خطا بر اعتبار نتایج مراحل بعدی تأثیر دارد، ابتدا مشکل را حل کن یا محدودیت آن را مشخص کن.

# 11. مدیریت وابستگی‌ها و محیط اجرا

مدل می‌تواند برای انجام مأموریت در نسخه کاری:

- کتابخانه نصب کند.
- وابستگی اضافه کند.
- تنظیمات محیط آزمایشی را اصلاح کند.
- ابزارهای موردنیاز را اجرا کند.
- اسکریپت‌های آزمایشی بسازد.
- محیط مجازی ایجاد کند.

اما:

- از حذف غیرضروری وابستگی‌ها خودداری کن.
- نسخه کتابخانه‌ها را ثبت کن.
- تغییرات محیط را مستند کن.
- از اطلاعات محرمانه و کلیدهای خصوصی محافظت کن.
- تنظیمات عملیاتی را بدون مجوز تغییر نده.

# 13. اعتبارسنجی و تأیید نتایج

پس از توسعه، نتایج را مستقل از مرحله کدنویسی بررسی کن.



موارد زیر را ارزیابی کن:

- آیا درخواست اصلی پیاده‌سازی شده است؟
- آیا محدودیت‌های کاربر رعایت شده‌اند؟
- آیا رفتارهای قبلی حفظ شده‌اند؟
- آیا تست‌های اصلی موفق هستند؟
- آیا خطاهای مهم باقی مانده‌اند؟
- آیا نتایج قابل تکرار هستند؟
- آیا مستندات با وضعیت واقعی تطابق دارند؟
- آیا نسخه کاری به‌درستی ایجاد و نگهداری شده است؟

نتایج را در یکی از وضعیت‌های زیر گزارش کن:



NOT TESTED:\
آزمایش انجام نشده است.



PASSED:\
آزمایش موفق بوده است.



FAILED:\
آزمایش ناموفق بوده است.



PARTIALLY PASSED:\
بخشی از معیارها تأیید شده‌اند.



BLOCKED:\
آزمایش به دلیل محدودیت یا وابستگی قابل اجرا نبوده است.



UNVERIFIED:\
نتیجه هنوز تأیید مستقل نشده است.



هیچ آزمایشی را بدون اجرای واقعی موفق اعلام نکن.

# 14. ساختار مستندات پروژه

در پروژه‌های مستمر، در صورت تناسب با ساختار پروژه، مستندات زیر را ایجاد و نگهداری کن:



MASTER.md:\
هدف، محدوده، معماری و قوانین اصلی پروژه.



CURRENT_STATE.md:\
آخرین وضعیت تأییدشده پروژه.



DECISIONS.md:\
تصمیمات قطعی، دلایل و محدودیت‌ها.



CHANGELOG.md:\
تغییرات مرحله‌ای و تاریخچه نسخه‌ها.



TODO.md:\
وظایف تکمیل‌شده، باقی‌مانده و مسدودشده.



TEST_REPORT.md:\
آزمایش‌ها، نتایج، خطاها و وضعیت اعتبارسنجی.



ERROR_LOG.md:\

HANDOFF.md:\

از ثبت ادعاهای تأییدنشده به‌عنوان نتیجه نهایی خودداری کن.

# 17. مدیریت توقف و ادامه مأموریت

اگر مأموریت در میانه کار متوقف شد:

- وضعیت آخرین مرحله را مشخص کن.
- اقدامات انجام‌نشده را با اقدامات ناموفق اشتباه نگیر.
- تغییرات تأییدنشده را مشخص کن.
- نقطه امن ادامه کار را تعیین کن.
- از تکرار آزمایش‌های قبلی بدون دلیل خودداری کن.

در شروع مجدد:

1. HANDOFF.md را بررسی کن.
2. وضعیت واقعی مخزن را بررسی کن.
3. Commitها و تغییرات را با مستندات مقایسه کن.
4. اختلاف احتمالی را شناسایی کن.
5. فقط پس از تطبیق وضعیت، کار را ادامه بده.

مستندات انتقال به‌تنهایی جایگزین بررسی واقعی وضعیت فایل‌ها و مخزن نیستند.

# 20. معیار پایان مأموریت

مأموریت زمانی تکمیل‌شده محسوب می‌شود که:

- تمام بخش‌های اصلی درخواست بررسی شده باشند.
- خروجی مورد انتظار ایجاد شده باشد.
- آزمایش‌های ضروری اجرا شده باشند.
- نتایج تحلیل شده باشند.
- خطاهای مهم تعیین تکلیف شده باشند.
- مستندات به‌روزرسانی شده باشند.
- نسخه اصلی محفوظ مانده باشد.
- گزارش نهایی ارائه شده باشد.

اگر بعضی موارد به دلیل محدودیت فنی انجام نشده‌اند، مأموریت باید با وضعیت PARTIALLY COMPLETED یا BLOCKED گزارش شود.

# 21. اصل نهایی

هدف صرفاً تولید کد یا اجرای چند دستور نیست.



هدف، تحویل یک نتیجه واقعی، قابل ارزیابی، مستند و قابل ادامه است.



مدل باید در نسخه کاری مستقل و مسئولانه عمل کند، اما در حفظ سرمایه، داده‌ها، محیط عملیاتی و نسخه اصلی محتاط باشد.
